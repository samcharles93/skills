# Incremental Adoption Strategy for Existing Codebases

Introducing strict linting into an established Go codebase often yields hundreds or thousands of pre-existing violations. Blocking builds or requiring massive fix PRs stalls velocity.

`golangci-lint` v2 provides targeted features to gate **only new changes** while allowing legacy code to be remediated incrementally.

---

## 1. Gating New Code Only

The most effective adoption pattern is filtering issues by git revision so that PR checks pass as long as new/modified code introduces zero new violations.

### `issues.new-from-merge-base` (Recommended for CI)

Compares the current `HEAD` against the common ancestor with the target branch (e.g. `main` or `master`):

```yaml
version: "2"

issues:
  # Show only new issues created after the merge-base against main
  new-from-merge-base: main
  # Check only modified lines, not full files touched by a change
  whole-files: false
```

### `issues.new-from-rev`

Measures changes against a fixed git commit or ref (e.g., `HEAD~1` or a release tag):

```yaml
version: "2"

issues:
  new-from-rev: HEAD~1
```

### `issues.new`

Measures unstaged/staged changes locally against `HEAD`:

```yaml
version: "2"

issues:
  new: true
```

---

## 2. Threshold Calibration & De-duplication

During early adoption phases, limit the noise from high-frequency linters using issue counts:

```yaml
version: "2"

issues:
  # Maximum issues reported per linter (0 = unlimited)
  max-issues-per-linter: 0

  # Maximum issues reported with identical text (0 = unlimited)
  max-same-issues: 0

  # Deduplicate issues on the same file + line
  uniq-by-line: true
```

---

## 3. Targeted Test & Generated Code Exclusions

Test code (`_test.go`) and autogenerated code (Mocks, Protobufs, OpenAPI) require different rules than production domain code.

```yaml
version: "2"

linters:
  exclusions:
    # Exclude strict generated files (following "// Code generated ... DO NOT EDIT.")
    generated: strict

    # Path glob patterns to exclude from analysis entirely
    paths:
      - "**/vendor/**"
      - "**/*.pb.go"
      - "**/mock_*.go"

    # Per-path linter rules
    rules:
      # Relax strict error and security checks in unit test files
      - path: _test\.go
        linters:
          - errcheck
          - gosec
          - noctx
          - forbidigo
          - dupl

      # Disable magic number checks in configuration or test files
      - path: (config\|_test)\.go
        linters:
          - mnd
```

---

## 4. Phased Adoption Roadmap

1. **Phase 1 (Baseline)**: Enable `default: standard` with `new-from-merge-base: main`. Enable `formatters` (`gofmt`/`gofumpt`).
2. **Phase 2 (Clean New Code)**: Ensure all PRs pass clean for new code.
3. **Phase 3 (Package Remediation)**: Remove `new-from-merge-base` package-by-package or file-by-file as legacy packages are refactored.
4. **Phase 4 (Strict CI)**: Require full repo compliance without `new-from-merge-base`.
